# Architecture

## Shape

This repository is a pnpm workspace with two deployable applications and two shared packages:

- `apps/web` is a Next.js App Router frontend. It calls the API through `lib/api.ts`; authentication is sent with an httpOnly cookie and only the display role is kept in `localStorage` for the current dashboard UI.
- `apps/api` is a NestJS REST API. Modules own auth, users, listings, and bookings; Prisma provides the database boundary.
- `packages/types` owns Zod input schemas and shared TypeScript output types.
- `packages/config` owns shared TypeScript configuration.
- `prisma` owns the PostgreSQL schema and seed data.

The normal flow is browser -> Next UI -> Nest API -> Prisma -> PostgreSQL. Authentication uses bcrypt password hashes and signed HS256 JWTs. A booking is created as `pending`; a creator confirms it, which calls `PaymentService.capture()` before setting status to `confirmed`.

## Product experience

The web experience serves two audiences through the same small surface:

- Clients start in the directory, compare creator offerings, inspect price and description, and request a date.
- Creators start in Studio, see incoming booking requests, confirm work, and can add a listing.

The interface uses a warm editorial studio system rather than a generic dashboard palette. Paper texture, ink typography, coral/cobalt/moss accents, and contact-sheet shapes signal craft and visual authorship. Functional surfaces remain compact: forms use obvious labels, status uses plain text, and primary actions stay consistent across roles.

## Local data

The seed creates admin, creator, and client users plus a listing and pending booking. The committed initial migration in `prisma/migrations` makes a fresh PostgreSQL database reproducible. Seeded accounts use the documented demo password; new passwords are stored only as bcrypt hashes.

The checked-in OpenAPI file is generated by `corepack pnpm openapi:export` from the Nest controller metadata. The exporter uses a database-independent module so documentation can be refreshed without a running PostgreSQL instance.

## Production integration plan

The current `AuthService` and `AuthGuard` use signed JWTs and bcrypt password hashes. Keep `JWT_SECRET` private and sufficiently random in every environment. The API sets an httpOnly `SameSite=Lax` cookie and the web client sends credentialed requests. Production should use HTTPS with same-site custom subdomains such as `app.example.com` and `api.example.com`; the API rejects state-changing requests with a mismatched `Origin`.

Replace `PaymentService` with Stripe Connect: create a PaymentIntent for the creator-connected account when a booking is requested, persist its ID, capture after confirmation, and process asynchronous webhook events for payment success, failure, refunds, and disputes. Do not treat the browser response as payment authority.
